# 13. Отзывчивость и память большой доски

Статус: не начата. Приоритет: P1; triage: ready-for-agent. GitHub Issue: не опубликована. Публикация подготовленных performance-карточек требует авторизации пользователя после автоматического отказа для карточки 12; повторная попытка не выполнялась.

## Проблема

[Профиль 09](../research/load-profile.md): в первом прогоне p95 интервала кадра при настоящем drag 483 ms (бюджет 50 ms), JS heap страницы 210.7 MiB (бюджет 150 MiB). 1000 DOM-нод и 998 связей отображаются в каждом из 10 контекстов. Профиль подтверждает пропуски кадров, но не локализует все источники затрат. `App.tsx` пересоздаёт данные всех нод при изменении присутствия и ищет prior через `current.find`; проверить стоимость React reconciliation, React Flow, связей и миникарты, а не делать вывод только по чтению кода.

## Работа и критерии готовности

- Снять CPU/React профиль реального drag и presence при 1000/10; отделить затраты React/DOM от доставки полной структуры (задача 12) и измерительного инструмента.
- Сохранить идентичность неизменившихся данных, сократить поиск/обновление нод и при необходимости отрисовывать только видимую часть доски. Сохранить корректность выделения, совместных курсоров, связей, миникарты, copy/paste и Undo/Redo.
- Два полных запуска профиля 09: p95 frame interval ≤50 ms, JS heap ≤150 MiB на страницу, загрузка ≤5 s. Если появляются новые ограничения, записать измерения и отдельную задачу вместо объявления gate пройденным.
- Дополнить измерения 30-минутным чередованием редактирования, переходов между диалогами и открытием/закрытием редакторов. Проверить, возвращается ли heap после сборки мусора к устойчивому диапазону; не считать краткий baseline доказательством отсутствия утечки.
- Typecheck, все серверные/e2e тесты, build. Обновить отчёт и PROGRESS; подтвердить бюджеты ACK/доставки совместно с задачей 12.

Зависимость: 09. Связана с [12](12.md); обе блокируют подтверждение отзывчивости 1000/10 для v1.
